- 失败交接：`terra-medium` 的完整 IPv4 正则在 10 个用例中通过 9 个；失败用例中 `192.168..1` 的期望是不计为无效地址，但完整匹配会因为空段而将其计入。

## 根因

题目要求检查的是三个明确条件，而不是判断字符串能否完整匹配通常意义上的 IPv4：

1. 点的数量不是 3（也就是段数少于或多于 4）；
2. 某个数字段以 `0` 开头且长度大于 1；
3. 某个数字段的值大于 255。

判题反馈表明，空段本身不属于后两类违规；`192.168..1` 有 3 个点，所以也不属于第一类。原方案把“空段”额外当作无效条件，扩大了筛选范围。

## 算法

先用 `LENGTH(ip) - LENGTH(REPLACE(ip, '.', ''))` 统计点数，不等于 3 时直接判为无效。

再用带段边界 `(^|\.)` 和 `(\.|$)` 的正则查找明确违规的数字段：

- `0[0-9]+`：长度至少为 2 的前导零段；
- `25[6-9]`：256 到 259；
- `2[6-9][0-9]`：260 到 299；
- `[3-9][0-9]{2}`：300 到 999；
- `[0-9]{4,}`：至少四位的数字，一定大于 255（若有前导零，也已经属于前导零违规）。

筛出满足任一条件的行后按 `ip` 分组计数，最后依次按 `invalid_count`、`ip` 降序排列。

## 正确性证明

对任意一行 `ip`：

- 若点数不为 3，则分隔得到的段数不是 4，查询的第一个条件会选中它。
- 若存在前导零数字段，该段必可写成 `0` 后接至少一个数字，并位于字符串开头/点之后和字符串结尾/点之前，因此正则的 `0[0-9]+` 分支会选中它；反之，该分支匹配到的必是一个长度大于 1 且以 `0` 开头的完整数字段。
- 对没有前导零的数字段，值大于 255 当且仅当它是 256–259、260–299、300–999，或长度至少为 4；这四类恰由其余正则分支穷尽，且段边界保证只匹配完整段。

所以查询选中的行恰好满足题面三种无效条件之一。空段不匹配任何数字段分支，因而不会引入判题未定义的额外无效条件。分组后的 `COUNT(*)` 正好是每个无效 IP 的出现次数，排序也与题意一致。

## 复杂度

设日志行数为 `N`，IP 字符串最大长度为 `L`，不同无效 IP 数为 `U`。每行的点计数和正则扫描均为 `O(L)`，总时间复杂度为 `O(NL)`；分组占用 `O(U)` 额外空间（不计数据库排序与执行器内部常数开销）。

## 边界与本地验证

- 点数：覆盖 0、1、2、3、4 个以上的点。
- 数值边界：覆盖 `0`、`00`、`01`、`255`、`256`、`299`、`300`、`999`、`1000`。
- 段位置：违规段分别位于首段、中间段和末段。
- 失败回归：`127.0.0.1` 与 `192.168..1` 均不被筛出。
- 聚合排序：重复无效 IP 先按计数降序，同计数再按 IP 降序。

本地使用独立的“拆点后逐条件判断”oracle，与 SQL 条件的等价实现对 1,508,597 个由 1 至 5 段、17 种边界段值组合出的字符串进行枚举对拍，差异数为 0。题目示例的聚合结果也精确复现为 `256.1.2.3 -> 2`、`192.168.001.1 -> 2`、`192.168.1 -> 1`；最终 SQL 的身份、点数条件、分组、双降序以及本文的证明与复杂度章节均通过静态检查。当前环境没有可用的 MySQL 客户端，未执行数据库引擎语法测试，也未使用远程判题。
