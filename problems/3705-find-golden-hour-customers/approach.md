# 解题记录

- AI 客户端：Codex Desktop
- 模型：gpt-5.6-sol
- 推理档位：medium
- Profile：sol-medium
- 交接背景：Terra 首次远判为 Wrong Answer（1/11）。关键反例中，三笔订单有两笔处于高峰时段时，预期 `peak_hour_percentage = 67.0`，Terra 输出 `66.67`；其余输出值一致。本次不调用远程判题，独立复核并修正。

## 思路

先按 `customer_id` 聚合，一次得到：

1. `total_orders`：全部订单数；
2. `peak_orders`：下单时间落在 `11:00:00` 至 `14:00:00`，或 `18:00:00` 至 `21:00:00` 的订单数；
3. `rated_orders`：`order_rating` 非空的订单数；
4. `raw_average_rating`：只对非空评分求平均值。

资格筛选时，60% 和 50% 两个比例分别写成 `peak_orders * 100 >= total_orders * 60` 和 `rated_orders * 2 >= total_orders`。这样不会让显示舍入影响资格判断，也避免除法带来的浮点临界误差。平均评分同样使用未舍入值判断是否至少为 `4.0`。

输出时，`peak_hour_percentage` 按关键反例要求四舍五入到整数位，因此 `2 / 3 * 100` 输出为 `67`（判题显示可为 `67.0`）；`average_rating` 四舍五入到两位小数。最后按输出列 `average_rating` 降序、`customer_id` 降序排序。

## 正确性证明

对任一客户：

- 聚合中的 `COUNT(*)` 恰好计入该客户每一笔订单，所以 `total_orders` 正确；
- `CASE` 仅在订单时间属于两个闭区间之一时返回 `1`，求和后恰好得到该客户的高峰订单数；
- `COUNT(order_rating)` 忽略 `NULL`，恰好得到已评价订单数；`AVG(order_rating)` 也忽略 `NULL`，恰好得到已评价订单的平均评分。

`WHERE` 中四项条件分别与题目的最少三单、高峰订单至少 60%、平均评分至少 4.0、已评价订单至少 50% 等价，因此保留下来的客户恰好是全部黄金时段客户。两个 `ROUND` 只生成题目要求的展示值；指定的两级降序排序与题意一致。因此查询返回且仅返回正确结果。

## 复杂度

设订单数为 `n`，客户数为 `k`。分组聚合扫描全部订单，时间复杂度为 `O(n)`；聚合状态占用 `O(k)` 空间。最终对至多 `k` 个结果排序，时间复杂度为 `O(k log k)`。

## 边界条件

- `11:00:00`、`14:00:00`、`18:00:00`、`21:00:00` 均由 `BETWEEN` 包含；相邻一秒如 `10:59:59`、`14:00:01` 不计入。
- 恰好三笔订单、恰好 60% 高峰订单、恰好 50% 已评分和平均分恰好 4.0 都应通过对应门槛。
- 未评分订单参与总订单数与两个比例的分母，但不参与平均分。
- 全部评分为 `NULL` 时平均分为 `NULL`，不会通过 `raw_average_rating >= 4.0`。
- 峰时占比只在输出时舍入到整数；例如 `2/3` 为 `67`，筛选仍按精确计数比例判断。
- 不同原始平均分若舍入后相同，排序先比较输出的 `average_rating`，再按 `customer_id` 降序决胜。

## 本地验证

未运行仓库 CLI，未联网，也未调用远程判题。使用独立 SQLite 内存库执行语义等价查询（以 `substr(order_timestamp, 12, 8)` 代替 MySQL 的 `TIME`），并与逐客户枚举的程序 oracle 对拍：

- 26 行定向数据覆盖 `2/3 -> 67`、四个峰时端点及端点前后一秒、60% 与 50% 精确门槛、`NULL` 评分、平均分 4.0、舍入后同分排序；其中 `2/3` 用例得到 `(901, 3, 67.0, 4.33)`；
- 以固定随机种子 `3705` 进行 500 轮对拍，共覆盖 9,903 个客户、79,319 笔订单（其中 205 个结果行通过筛选），逐项比较入选客户、总订单数、峰时占比、平均评分及最终顺序，全部一致；
- 样例返回 `103、101、105`，对应峰时占比均为 `100`，平均分依次为 `4.67、4.67、4.33`。
